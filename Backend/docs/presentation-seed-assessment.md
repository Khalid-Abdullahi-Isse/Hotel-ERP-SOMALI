# Presentation seed assessment (2026-09-27)

## Target and safety result

The intended target is **only** the PostgreSQL service in the root `docker-compose.yml` project `somali-hotel-erp`. The root `.env` supplies that service's credentials and host port. `Backend/.env` has a different password and cannot authenticate to the running Compose database.

The Compose `hotel_erp` database currently has **zero tables** (`public."Hotel"` is absent). The API health endpoint returns 200 because its readiness check confirms database connectivity, not application schema readiness. No presentation records were inserted.

The existing migration chain cannot be applied under the request's absolute ban on destructive migrations: `20260817001000_auth_rbac` contains `TRUNCATE TABLE "RefreshToken"` and drops a column. Other migrations drop columns, constraints, triggers, or indexes. Even though this database is currently empty, the seed must not silently execute that chain. Applying only `prisma db push` would omit the SQL integrity triggers in the migrations. A schema initialization decision is required before the presentation seed can be run or validated.

## Architecture and entity dependency map

NestJS controllers use Prisma with PostgreSQL; Redis supplies caching. Next.js server services call the `/api/v1` routes. The tenant boundary is `hotelId` on operational and accounting records. System roles are `ADMIN`, `MANAGER`, and `STAFF`; permissions are defined in `src/auth/auth.constants.ts`.

`Hotel -> Role/Permission/User`, `Floor/RoomType -> Room`, `Guest + Room -> Reservation -> ReservationRoom -> Charge/Invoice/Payment`, `Room -> HousekeepingTask/MaintenanceRequest`, `ExpenseCategory + PaymentMethod + User -> Expense`, `Account + AccountingJournal + FiscalPeriod -> JournalEntry -> JournalLine`. `AuditLog` has a hotel and optional user and stores an entity type and UUID.

## Seed design constraints discovered

- Presentation hotel must have its own code and logins so no existing hotel's data is changed.
- Existing scripts such as `scripts/seed-realistic.mjs` do not satisfy this request: they require a preexisting administrator, generate thousands of guests/reservations, directly insert accounting-sensitive operations, and include an option that resets user passwords.
- A month with roughly 60% occupancy in a 72-room hotel needs about 1,300 occupied room nights. A few hundred short reservations across five months cannot achieve that; the generator should include credible longer corporate stays or more reservations, then validate the measured occupancy from underlying reservation room nights.
- The current frontend uses paginated API lists and server-side adapters; its key screens read the routes in the map above. A successful seed must be verified with those read endpoints and an authenticated presentation hotel user.

## Seed implementation prepared

`scripts/presentation-plan.mjs` builds a deterministic scenario anchored to a hotel-local business date: 72 rooms in seven categories, 160 fictional guests, 390 reservations, 90 expenses, and 30 maintenance requests. The active reservation mix targets 52 occupied rooms (72.2%), four arrivals today, four checkouts today, active housekeeping, and one room in maintenance. Four prior months have occupied-night targets around 55%, 63%, 68%, and 71% before normal calendar variation.

`scripts/presentation-seed.mjs` has an explicit `ALLOW_PRESENTATION_SEED=true` write guard and uses the root Compose `.env` connection only. `pnpm run seed:presentation --dry-run` prints the plan and current counts without writes. A live run also requires `PRESENTATION_PASSWORD` (12–128 characters) for the seed-owned accounts. It creates a marked `PRESENTATION_MOG` hotel, checks for marker collisions, uses transactions for each logical unit, and calls the application's accounting posting services for charges, payments, and expenses. It does not attach to application startup. `--validate-only` checks seeded counts, balanced journals, overlapping stays, and live room/reservation status groups.

The command has **not** been run in write mode because the selected Compose database lacks the application schema. Its runtime behavior and API output remain unverified until that prerequisite is completed. The seed must be reviewed against the initialized database before any write execution.

Run `node scripts/presentation-preflight.mjs` from `Backend/`. It reads the root Compose `.env`, connects only to `127.0.0.1` at the Compose PostgreSQL host port, and prints database/schema and hotel counts. It does not mutate the database.
